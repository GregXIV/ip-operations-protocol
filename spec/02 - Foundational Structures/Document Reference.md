# Document Reference

> Reference structure for any document mentioned in protocol messages.

Used wherever the protocol references documents — office forms, search reports, granted texts, deliverables, evidence files, payment receipts, internal artifacts. The protocol carries references and access semantics, not document internals (per [Non-Scope](../01%20-%20Front%20Matter/Non-Scope.md)).

## Structure

### `documentUri`
Type: URI, required

Stable identifier of the form `urn:ipproto:document:{uuid}`. Generated by the originating actor when the document first enters the protocol.

### `documentType`
Type: URI, required

Typed classification. Standard types in `urn:ipproto:doctype:` namespace:

**Office-issued:**
- `officeForm` — numbered or named office form (Form 2004C, Form 2006A, Form UP7000)
- `officeDecision` — decision document
- `officePublication` — published patent document (A1, B1, T2)
- `officeRegisterEntry` — register entry record

**Applicant-side:**
- `applicantSubmission` — anything filed by the applicant
- `applicantDraft` — pre-filing or unfiled drafts
- `translation` — claim or full-spec translations

**Service-provider:**
- `serviceDeliverable` — outputs from service providers
- `servicePreparedArtifact` — artifacts prepared for client action

**Evidence:**
- `executionEvidence` — confirmation receipts, screenshots
- `paymentEvidence` — payment confirmations
- `filingReceipt` — proof that a filing was received by an office (added in 0.2)
- `officialFeeReceipt` — proof that an official fee was paid (added in 0.2)

**Commercial:**
- `invoice` — an invoice as a document, referenced by [Invoice Issued](../03%20-%20Messages/Payments/Invoice%20Issued.md) (added in 0.2). Before 0.2 `invoice` existed only as a deliverable type

`filingReceipt` and `officialFeeReceipt` are the standard labels for what a provider hands back after a filing or a fee payment; a [Work Instruction](../03%20-%20Messages/Work%20Instruction/Work%20Instruction.md) names them in `expectedDeliverables`. They classify the document. The evidence type `urn:ipproto:evidence:officeFeeReceipt` of an [Evidence Collection](Evidence%20Collection.md) classifies the evidence item that may point at such a document.

Custom types allowed through namespaced URNs.

### `documentKind`
Type: structured, optional

More specific subtype. For an office form, the form identifier; for a publication, the kind code; for a deliverable, the deliverable category. Sub-fields: `kindCode`, `kindAuthority` (URN for who defines this kind).

### `assetReferences`
Type: array of [Asset Reference](Asset%20Reference.md) URIs, conditional (at least one entry)

Which assets the document relates to. Required where the document relates to an existing asset.

Omitted, since 0.3, where it relates to none: the draft of an application that is not yet filed, an invention disclosure, the invoice for a subscription that covers no asset. Until 0.3 the field was required without exception, so such a document could not be described. A reference issued for the document after the asset has been bootstrapped names the asset. See *Work on a right that does not exist yet* in [Workstream](Workstream.md).

### `originator`
Type: [Actor Reference](Actor%20Reference.md) URI, required

Who originated the document. The originator is typically the authoritative source for the document's content.

### `originationDate`
Type: ISO 8601 datetime, required

### `languageCode`
Type: ISO 639-1, optional

Primary language. Required when content matters for downstream processing.

### `storageLocations`
Type: array of structured entries, required (at least one)

Where the content lives. Each entry:
- `locationUri` — URI of the location
- `locationType` — enumeration: `httpsRest`, `s3Bucket`, `vault`, `officeRegister`, `email`, `filesystem`, `other`
- `accessRequirements` — optional structured: `authMethodHint`, `credentialIssuerActorUri`, `accessExpiresAt`
- `mediaType` — IANA media type
- `contentHash` — optional, structured: `algorithm`, `value`
- `contentSizeBytes` — optional integer
- `pageCount` — optional integer

### `structuredContentReference`
Type: structured, optional

When the document has a known structured schema (typically ST.96):
- `schemaIdentifier` — URI of the schema
- `schemaConformanceLevel` — enumeration: `strict`, `extended`, `partial`
- `structuredContentLocation` — optional pointer to structured representation

### `supersedes`, `supersededBy`, `versionLabel`, `derivedFrom`, `relatedDocuments`
Optional, for version chains and document relationships. See worked examples below.

## Worked example — EPO Form 2004C

```json
{
  "documentUri": "urn:ipproto:document:f8e2c91a-...",
  "documentType": "urn:ipproto:doctype:officeForm",
  "documentKind": {
    "kindCode": "Form 2004C",
    "kindAuthority": "urn:ipproto:office:epo"
  },
  "assetReferences": ["urn:ipproto:asset:7c4f9a82-..."],
  "originator": "urn:ipproto:actor:epo",
  "originationDate": "2026-04-28",
  "languageCode": "en",
  "storageLocations": [
    {
      "locationUri": "https://register.epo.org/application?number=EP21712345&tab=doclist",
      "locationType": "officeRegister",
      "accessRequirements": {"authMethodHint": "publicAccess"},
      "mediaType": "application/pdf",
      "pageCount": 42
    }
  ],
  "versionLabel": "Form 2004C"
}
```

## Worked example — service deliverable with structured content

```json
{
  "documentUri": "urn:ipproto:document:9c2e4f81-...",
  "documentType": "urn:ipproto:doctype:serviceDeliverable",
  "documentKind": {
    "kindCode": "validation-analysis",
    "kindAuthority": "urn:ipproto:scheme:meridian-deliverables"
  },
  "assetReferences": ["urn:ipproto:asset:7c4f9a82-..."],
  "originator": "urn:ipproto:actor:meridian-ip-group",
  "originationDate": "2026-05-05T14:30:00Z",
  "languageCode": "en",
  "storageLocations": [
    {
      "locationUri": "https://deliverables.meridian-ip-group.example/asset/7c4f9a82/validation-analysis.pdf",
      "locationType": "httpsRest",
      "accessRequirements": {
        "authMethodHint": "oauth2",
        "credentialIssuerActorUri": "urn:ipproto:actor:meridian-ip-group"
      },
      "mediaType": "application/pdf",
      "contentHash": {"algorithm": "SHA-256", "value": "3a7bd9e2..."},
      "contentSizeBytes": 1452678
    }
  ],
  "structuredContentReference": {
    "schemaIdentifier": "urn:meridian-ip-group:deliverables:validation-analysis:v3",
    "schemaConformanceLevel": "strict"
  }
}
```

## Worked example — draft for a right that does not exist yet

Added in 0.3. The draft of a trademark application, delivered before the filing. No asset exists, so the reference carries no `assetReferences`.

```json
{
  "documentUri": "urn:ipproto:document:4e7a19c2-...",
  "documentType": "urn:ipproto:doctype:applicantDraft",
  "originator": "urn:ipproto:actor:woodgrove-ip",
  "originationDate": "2026-11-27T15:10:00Z",
  "languageCode": "en",
  "storageLocations": [
    {
      "locationUri": "https://deliverables.woodgrove-ip.example/d-trademark-filing-001/northwind-aero-em-draft.pdf",
      "locationType": "httpsRest",
      "mediaType": "application/pdf"
    }
  ],
  "versionLabel": "Draft 1"
}
```

## Behavior

Documents are **federated** — content lives wherever the originating actor stores it, and receivers fetch on demand. The protocol does not store content. Documents superseded by later versions are preserved (never deleted); the supersedes/supersededBy chain is the audit trail.
