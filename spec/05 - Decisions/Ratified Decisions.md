# Ratified Decisions

> Decisions made during v0.1 design that are positioned as defaults; subject to consortium ratification but recommended as-is.

The protocol's design accumulated 28 open positions across the per-message and consolidation work. Most are conservative-direction choices that simplify v0.1 and are easy to revisit in v1.x. Listed here as recommended ratifications.

## Asset reference

1. **Protocol-assigned URI is canonical.** Office identifiers are descriptive; the protocol-assigned URN is stable across the asset's lifetime.
2. **Identifier change history is append-mostly.** Old identifiers remain valid historical references but may be flagged superseded; never deleted.

## Actor reference

3. **Actor type extensibility is controlled.** Standard actor types are enumerated in the spec; custom types use namespaced URNs.
4. **Role enumeration is flat for v0.1.** Hierarchical role taxonomies deferred to v1.x.

## Authority claim

5. **Authority claims are stored in record's `_authority` meta-section.** No separate registry; claims live with the records they govern.
6. **Joint authority claim type not in v0.1.** v0.1 supports `exclusive`, `sourceOfTruth`, and `advisory`. Joint-claim semantics deferred to v1.x.
7. **Single claim reference per assertion.** [Data Assertion](../02%20-%20Foundational%20Structures/Data%20Assertion.md) cites exactly one [Authority Claim](../02%20-%20Foundational%20Structures/Authority%20Claim.md). Multi-claim assertions deferred.

## Identity resolution

8. **Identity confidence level is optional in v0.1 with strong recommendation.** Receivers may apply their own policy on low-confidence resolutions.
9. **Identity dispute severity is calibrated per-actor.** No global severity ranking; each actor decides.

## Document reference

10. **Document content hash is optional.** Strong recommendation for high-stakes documents (deliverables, evidence). Required only by receiver policy.
11. **Document storage broker is not in v0.1.** No protocol-mandated content distribution mechanism. Storage is federated; receivers fetch on demand.
12. **Document type extensibility is controlled.** Standard types enumerated; custom types use namespaced URNs.

## Workstream and milestone

13. **Milestone category extensibility is controlled.** Standard categories enumerated; custom categories use namespaced URNs.
14. **Execution mode is fixed in v0.1.** `serviceProviderManaged`, `selfService`, `thirdPartyRfp`. Custom modes deferred.
15. **Chain execution policy is `strict` only in v0.1.** Optimistic and manual policies deferred.

## Bootstrap and discovery

16. **Bootstrap is producer-initiated.** No on-demand asset creation; assets enter the protocol when an authorized producer publishes [Asset Bootstrap](../03%20-%20Messages/Bootstrap%20and%20Discovery/Asset%20Bootstrap.md).
17. **Acknowledgment vs. acceptance distinction in [Deliverable Acknowledged](../03%20-%20Messages/Deliverable%20Handoff/Deliverable%20Acknowledged.md) retained.** `simpleAcknowledgment`, `acceptance`, `conditionalAcceptance`, `objection` enum values.

## Workstream lifecycle

18. **No built-in retry mechanism.** Retries are modeled as new [Goal Decomposition](../03%20-%20Messages/Workstream%20Lifecycle/Goal%20Decomposition.md) proposals.
19. **Subscription modification uses terminate-and-restart.** No in-place subscription modification message in v0.1.
20. **No separate auto-resolution dispute message.** Auto-resolution through retroactive late-arriving events uses standard [Dispute Resolution Decision](../03%20-%20Messages/Disputes/Dispute%20Resolution%20Decision.md).

## Naming and structure (consolidation)

21. **Renamed `IdentityResolutionDecision` to [Dispute Resolution Decision](../03%20-%20Messages/Disputes/Dispute%20Resolution%20Decision.md).** Now handles all three dispute types uniformly.
22. **Status assertions move to envelope-level `assertions` array.** Per-message `statusAssertion` and similar fields eliminated; everything goes through the standard array.
23. **[Outcome Details](../02%20-%20Foundational%20Structures/Outcome%20Details.md) and [Evidence Collection](../02%20-%20Foundational%20Structures/Evidence%20Collection.md) extracted as foundationals.** Common shapes pulled out; per-message specs reference rather than redefine.
24. **UserContext field naming standardized.** Single `userContext` field name; qualifying prefixes only when two distinct contexts appear in one message.

## Adding RecordUpdate

25. **[Record Update](../03%20-%20Messages/Generic/Record%20Update.md) added as 23rd message.** Lightweight envelope for data-only updates that don't naturally fit operational messages. Used sparingly.

## Other

26. **Generic `serviceProviderManaged` execution mode rather than vendor-specific.** Implementations map the generic enum to whichever provider is configured as default.
27. **`partiallyConfirmed` outcome in [Asset Match Response](../03%20-%20Messages/Bootstrap%20and%20Discovery/Asset%20Match%20Response.md) deferred to v1.x.** v0.1 supports `confirmed`, `confirmedWithEnrichment`, `denied`, `unknown`, `disputedResolution`. Partial confirmation deferred.
28. **Asset bootstrap acceptance is implicit.** Receivers create local replicas without explicit acknowledgment; [Asset Match Inquiry](../03%20-%20Messages/Bootstrap%20and%20Discovery/Asset%20Match%20Inquiry.md)/[Asset Match Response](../03%20-%20Messages/Bootstrap%20and%20Discovery/Asset%20Match%20Response.md) handles validation.

## Version 0.2.0 (ratified 2026-10-01 and 2026-10-02)

29. **The protocol is extended for work requests, work instructions, invoices and procurement.** Ratified by the maintainer on 2026-10-01 and released as version 0.2.0, a minor and purely additive version: thirteen messages, two foundational structures ([Agreed Price](../02%20-%20Foundational%20Structures/Agreed%20Price.md), [Service Level](../02%20-%20Foundational%20Structures/Service%20Level.md)), new optional fields on [Workstream](../02%20-%20Foundational%20Structures/Workstream.md) and [Milestone](../02%20-%20Foundational%20Structures/Milestone.md), and new vocabulary values. Nothing existing is renamed or removed; a 0.1 receiver that degrades on unknown values, as [VERSIONING](../../VERSIONING.md) requires, keeps working and treats the additions as unknown. A receiver that validates strictly against the 0.1 schemas rejects the 0.2 values `softwareService` and `revenueShare` (this sentence was corrected in 0.3). The *Commercial terms* section of [Non-Scope](../01%20-%20Front%20Matter/Non-Scope.md) is amended with it: pricing models and contractual terms stay out of scope, while how a binding price, a bid and an award are exchanged is in scope. Decision 14 stands as it is — the execution modes remain fixed. The procurement messages, beginning with [Bid Invitation](../03%20-%20Messages/Procurement/Bid%20Invitation.md), give `thirdPartyRfp` its mechanics.
30. **A catalogue order may be the commitment in one step.** [Work Requested](../03%20-%20Messages/Workstream%20Lifecycle/Work%20Requested.md) carries an optional `preAuthorized` flag. When it is set and the request names an `offerReference`, the orchestrator's [Goal Decomposition](../03%20-%20Messages/Workstream%20Lifecycle/Goal%20Decomposition.md) counts as committed without a separate [Orchestration Committed](../03%20-%20Messages/Workstream%20Lifecycle/Orchestration%20Committed.md), provided every `agreedPrice` in it matches the offer. If a price differs, the flag has no effect and the requester commits as usual.

Decisions 31 to 36 follow the recommendations of the extension proposal. They were ratified by the maintainer on 2026-10-02.

31. **`orchestrator` is a role.** It was a glossary word in 0.1. [Work Requested](../03%20-%20Messages/Workstream%20Lifecycle/Work%20Requested.md) is addressed to the orchestrator, and addressing needs a role a receiver can check. Listed in [Actor Role Declaration](../02%20-%20Foundational%20Structures/Actor%20Role%20Declaration.md).
32. **The actor type list is open in the schema.** Decision 3 allows custom actor types as namespaced URNs, but the 0.1 schema held the standard types as a closed enumeration. Since 0.2 the schema accepts the standard types, now including `softwareService`, and any namespaced URN. See [Actor Reference](../02%20-%20Foundational%20Structures/Actor%20Reference.md).
33. **One invoice message.** [Invoice Issued](../03%20-%20Messages/Payments/Invoice%20Issued.md) serves supplier invoices and the customer invoice alike. Payee and payor say which it is.
34. **A small core line item vocabulary.** Five standard line item types in `urn:ipproto:lineItem:` — `professionalFee`, `translation`, `officialFee`, `handling`, `disbursement` — with custom types through namespaced URNs. See [Agreed Price](../02%20-%20Foundational%20Structures/Agreed%20Price.md).
35. **A missed service level is derived, not announced.** No message reports a missed [Service Level](../02%20-%20Foundational%20Structures/Service%20Level.md); each party derives it from timestamps. A message can be added later without breaking anything.
36. **The guiding principle speaks of IP operations.** The principle in [Non-Scope](../01%20-%20Front%20Matter/Non-Scope.md) read "patent-operations data layer" in 0.1. The asset model already covers trademarks and designs, so the wording is "IP-operations data layer".

## Version 0.3.0 (ratified 2026-10-02)

Follow-up decisions to 0.2.0, agreed by the maintainer on 2026-10-02. Version 0.3.0 is a minor version under the pre-1.0 rule of [VERSIONING](../../VERSIONING.md) and not purely additive: decisions 37, 40 and 45 relax rules a 0.2 receiver could rely on.

37. **A request and a workstream may describe rights still to be created.** [Work Requested](../03%20-%20Messages/Workstream%20Lifecycle/Work%20Requested.md) and [Workstream](../02%20-%20Foundational%20Structures/Workstream.md) carry `prospectiveRights` next to `assetReferences`, and at least one of the two is required. In 0.2 at least one asset was required, so a first filing or a drafting job could not be requested. Decision 16 stands: a prospective right is not an asset, and the asset a filing creates enters the protocol through [Asset Bootstrap](../03%20-%20Messages/Bootstrap%20and%20Discovery/Asset%20Bootstrap.md). The orchestrator then adds it to the workstream.
38. **A request can be declined inside the protocol.** [Request Declined](../03%20-%20Messages/Workstream%20Lifecycle/Request%20Declined.md) is the orchestrator's answer to a request it will not serve, with a reason category and an optional narrative. A declined request creates no workstream.
39. **A withheld requester is disclosed by a message.** [Requester Disclosed](../03%20-%20Messages/Procurement/Requester%20Disclosed.md) carries the requester's [Actor Reference](../02%20-%20Foundational%20Structures/Actor%20Reference.md) from the orchestrator to one bidder. It is sent only where the [Bid Invitation](../03%20-%20Messages/Procurement/Bid%20Invitation.md) withheld the identity, only after that bidder attested `clear`, and never to a bidder that attested `conflict`.
40. **An invoice line refers to a milestone or to a subscription.** Each line of [Invoice Issued](../03%20-%20Messages/Payments/Invoice%20Issued.md) carries exactly one of `milestoneReference` and `subscriptionReference`. In 0.2 every line needed a milestone, so a subscription could not be invoiced line by line.
41. **The tax treatment vocabulary is open and provisional.** `taxed`, `reverseCharge`, `exempt` and `outsideScope` stay as standard values of `taxTreatment`; custom values use namespaced URNs. The values are not settled by this decision: nobody who issues invoices has reviewed them. See [Open Questions for Consortium](Open%20Questions%20for%20Consortium.md), question 7.
42. **Free-text messaging is outside the protocol.** Decided on 2026-10-01 with the 0.2.0 extension and written into [Non-Scope](../01%20-%20Front%20Matter/Non-Scope.md) in 0.3.
43. **The requester identifies a beneficiary that is not an actor.** Its identifier is the `resolvedEntityUri` the requester gives in the beneficiary's [Entity Reference](../02%20-%20Foundational%20Structures/Entity%20Reference.md). The `ultimateBeneficiary` role declaration is optional in that case. See [Workstream](../02%20-%20Foundational%20Structures/Workstream.md).
44. **A revenue share is exchanged between provider and contract holder only.** The `commercialTerms` that carry `sharePercent` do not travel to the subscriber, whose message for the same subscription states its own terms. See [Service Subscription Started](../03%20-%20Messages/Subscriptions/Service%20Subscription%20Started.md).

45. **A Document Reference need not name an asset.** `assetReferences` in [Document Reference](../02%20-%20Foundational%20Structures/Document%20Reference.md) is required only where the document relates to an existing asset. This follows from decision 37: the draft a drafting job delivers, or the invoice for a subscription without assets, relates to none. In 0.2 the field was always required.
46. **`subscriptionFee` is a sixth standard line item type.** It names the recurring fee of a subscription on an invoice line that carries a `subscriptionReference` (decision 40). This extends decision 34, whose five types all describe work on a milestone. See [Agreed Price](../02%20-%20Foundational%20Structures/Agreed%20Price.md).

## Version 0.4.0 (ratified 2026-10-02)

The six points that 0.3.0 left open, decided by the maintainer on 2026-10-02. Version 0.4.0 is a minor version and purely additive: three optional fields and three clarifications. No rule of 0.3 is relaxed or tightened, and a 0.3 message remains valid.

47. **A subscription may have one start message per audience.** Decision 44 is confirmed as written. Under one `subscriptionReference` the copy of [Service Subscription Started](../03%20-%20Messages/Subscriptions/Service%20Subscription%20Started.md) between the application's provider and the contract holder carries the terms with `sharePercent`, and the copy addressed to the subscriber states the subscriber's own terms. Keeping `sharePercent` out of the subscriber's copy is a rule the sender follows, not one a schema enforces.
48. **The orchestrator records a resulting asset; what is to be filed stays with the corporate claim.** On a [Workstream](../02%20-%20Foundational%20Structures/Workstream.md) the orchestrator's claim covers adding an asset URI to `assetReferences` and to the `resultingAssetReferences` of a prospective right, provided an [Asset Bootstrap](../03%20-%20Messages/Bootstrap%20and%20Discovery/Asset%20Bootstrap.md) exists whose `triggeringReference` names that workstream or one of its milestones. That is recording a fact. Adding, removing or otherwise altering `prospectiveRights` entries, and removing asset references, stay under the corporate claim over goal and chain. This completes decision 37, which had the orchestrator add the asset without saying under whose claim.
49. **A Bid Invitation may describe rights still to be created.** [Bid Invitation](../03%20-%20Messages/Procurement/Bid%20Invitation.md) carries an optional `scope.prospectiveRights` with the entries of [Work Requested](../03%20-%20Messages/Workstream%20Lifecycle/Work%20Requested.md). While `requesterIdentityWithheld` is true, `applicant` is left out of every entry, so that the invitation cannot reveal who is asking before the conflict check; the parties a bidder needs for the check are in `conflictParties`, as before. `scope` still requires neither `assetReferences` nor `prospectiveRights`, so a 0.3 invitation that describes the work in `scopeText` alone stays valid.
50. **A subscription line may state its billing period.** A line of [Invoice Issued](../03%20-%20Messages/Payments/Invoice%20Issued.md) that carries `subscriptionReference` may carry `billingPeriod`, with `from` and `to` as ISO dates, both inclusive, `to` not before `from`. The field is not allowed on a milestone line. This extends decision 40.
51. **The reason categories of Request Declined are confirmed.** The closed list of 0.3.0 stands: `serviceNotOffered`, `offerNotAvailable`, `requesterNotEligible`, `conflictOfInterest`, `noSupplierAvailable`, `insufficientInformation`, `other`. No change to [Request Declined](../03%20-%20Messages/Workstream%20Lifecycle/Request%20Declined.md) or its schema; this confirms the list that decision 38 left to the 0.3.0 text. The points listed under question 7 of [Open Questions for Consortium](Open%20Questions%20for%20Consortium.md), on the tax treatment vocabulary, are not decided by this and remain open.
52. **A Bid Invitation names the requester where its identity is not withheld.** [Bid Invitation](../03%20-%20Messages/Procurement/Bid%20Invitation.md) carries an optional `requester`, a full [Actor Reference](../02%20-%20Foundational%20Structures/Actor%20Reference.md) of the same shape as in [Requester Disclosed](../03%20-%20Messages/Procurement/Requester%20Disclosed.md). A 0.4 sender includes it when the requester's identity is not withheld. It is absent while `requesterIdentityWithheld` is true. It is not required in the other case, because a 0.3 invitation without it must stay valid. Requester Disclosed (decision 39) remains the message for the withheld case.

## Version 0.4.1 (ratified 2026-10-02)

Three rules for the sender of a [Bid Invitation](../03%20-%20Messages/Procurement/Bid%20Invitation.md), decided by the maintainer on 2026-10-02, after 0.4.0 was tagged, on points its build had left open. They are prose: no schema, no schema identifier and nothing on the wire changes, and `protocolVersion` stays `0.4`. Released as a patch version although it is more than editorial; the changelog says why.

53. **Every applicant is a conflict party.** An applicant of a prospective right who is neither the requester nor the beneficiary is listed in the invitation's `conflictParties`, with role `other` unless another role describes it. A bidder therefore sees every party it would act for before it bids, also while the requester's identity is withheld and `applicant` is left out of the entries (decision 49). No field is added to [Requester Disclosed](../03%20-%20Messages/Procurement/Requester%20Disclosed.md).
54. **A withheld invitation does not name the requester indirectly.** While `requesterIdentityWithheld` is true, no [Entity Reference](../02%20-%20Foundational%20Structures/Entity%20Reference.md) in the invitation carries the requester as its source (`source.sourceActorUri`) or names it in any other field. The orchestrator re-states such a reference under its own name or without a source actor. This is a rule the sender follows; the schema cannot check it. It completes decisions 49 and 52, which keep `applicant` and `requester` out of a withheld invitation.
55. **The sender may limit the intended jurisdictions on an invitation.** The `intendedJurisdictions` of an entry in `scope.prospectiveRights` may be limited to the jurisdictions the invitation covers; the sender is not required to show the full filing plan to a bidder. [Work Requested](../03%20-%20Messages/Workstream%20Lifecycle/Work%20Requested.md) and [Workstream](../02%20-%20Foundational%20Structures/Workstream.md) keep the full list. This replaces a sentence of the 0.4.0 text, which said that the entry is not cut down to the invitation.

## Version 0.5.0 (ratified 2026-10-04)

Twelve points raised by the first conformance reading of an orchestrator implementation against 0.4.1, decided by the maintainer on 2026-10-04. Decisions 56 to 67 follow the order of the points, so decision 55 + *n* answers point *n*.

56. **A message entered by another actor names it in `recordedBy`.** The envelope has an optional `recordedBy` with `actorUri` (required) and `userContext`. It is used where an actor enters a message on the originating actor's behalf with the originator's consent, for example the orchestrator's staff recording a supplier's acceptance given by telephone. `originatingActor` and `originatingRoleDeclaration` keep naming the originator, and the message binds it. `userContext` names only a user of the originating actor. The consent lies outside the message. See [Common Envelope](../02%20-%20Foundational%20Structures/Common%20Envelope.md).
57. **An invoice can be disputed and cancelled; acceptance stays implicit.** Two messages join the Payments category. [Invoice Disputed](../03%20-%20Messages/Payments/Invoice%20Disputed.md), from payor to payee, carries a closed reason category (`amountNotAgreed`, `workNotCompleted`, `notOrderedByPayor`, `duplicateInvoice`, `taxTreatmentIncorrect`, `formalDefect`, `other`) and may name disputed lines by their position and the disputed amount. [Invoice Cancelled](../03%20-%20Messages/Payments/Invoice%20Cancelled.md), from payee to payor, carries a closed reason category (`issuedInError`, `disputeAccepted`, `workAbandoned`, `other`) and may name the replacement invoice and a cancellation document of the new document type `creditNote`. There is no acceptance message: an invoice the payor does not dispute stands, and [Payment Authorized](../03%20-%20Messages/Payments/Payment%20Authorized.md), where used, is the payor's affirmative step. A dispute is not withdrawn by a message. Who is right stays between the parties, as [Invoice Issued](../03%20-%20Messages/Payments/Invoice%20Issued.md) already said.
58. **Service Deliverable's `assertions` is conditional.** The prose follows the schema: the field is present where the deliverable substantiates a section of a record and omitted where it substantiates none. The page had called it required since 0.1; the schema never did. No schema change. On [Deliverable Acknowledged](../03%20-%20Messages/Deliverable%20Handoff/Deliverable%20Acknowledged.md) the conditions on `conditions` and `objectionDetails` stay rules of the page, which now says so; the schema is left as it is.
59. **Records named by URI are resolvable from their issuer.** Actor References, Actor Role Declarations, Document References and Authority Claims that a message names by URI are resolvable from the actor that assigned the URI; the sender of a message answers for every record it names. The answer is the record in its schema's structure. The issuer serves at least the actors that produced or received a message naming the URI, and resolution discloses nothing a message may not. The transport stays open, as [Non-Scope](../01%20-%20Front%20Matter/Non-Scope.md) says for messages; an HTTPS shape is recommended, not required. See *Record resolution* in [Conventions](../01%20-%20Front%20Matter/Conventions.md).
60. **No change for instructions without agreed clocks or named deliverables: the data is fixed, not the protocol.** A [Work Instruction](../03%20-%20Messages/Work%20Instruction/Work%20Instruction.md) requires at least one service level, a `responseDeadline` that repeats the `dueAt` of the `acknowledgement` level, and at least one expected deliverable. An implementation that has no agreed clock or no named deliverable for a service does not fill the gap with an invented level or a placeholder deliverable type; it agrees an acknowledgement level in its terms and names at least one deliverable for every service it instructs. A service level is an agreed clock, and one nobody agreed is not a service level. No standard placeholder such as `asInstructed` is added. The schemas and the pages stay as they are.
61. **A provisional tax treatment `notStated`.** `taxHandling.taxTreatment` of [Invoice Issued](../03%20-%20Messages/Payments/Invoice%20Issued.md) gains the standard value `notStated`: the sender does not know the treatment. It claims nothing about the tax position, and the invoice document says what applies. It is for invoices recorded from documents whose tax position was not captured, not a substitute for a treatment the payee knows. Like the four values of 0.2 it is provisional under question 7 of [Open Questions for Consortium](Open%20Questions%20for%20Consortium.md), which stays open.
62. **A work requester that ends a provider's milestone abandons it; only the provider fails it.** [Milestone Failed](../03%20-%20Messages/Milestone%20Lifecycle/Milestone%20Failed.md) is produced by the actor with `primary` assignment, as written since 0.1, and only by it. Where the work requester, typically an orchestrator, ends a milestone because the provider did not perform, it sends [Milestone Abandoned](../03%20-%20Messages/Milestone%20Lifecycle/Milestone%20Abandoned.md) with itself as `decisionAuthority`, the deciding person in `decisionUserContext`, `reasonCategory` `other` and the reason in `reasonNarrative`. The alternative of letting the work requester declare failure for `deadlineMissed` was not taken: it would make one message mean two things depending on who sends it. No schema change and no new reason category.
63. **An orchestrator profile.** A new page, [Conformance](../01%20-%20Front%20Matter/Conformance.md), lists what an orchestrator implements: general requirements for every producer of messages, core requirements of the orchestrator, and conditional modules (procurement, payments, subscriptions, assets) that apply when the orchestrator does what they cover. Each requirement points at the page that states it; where they disagree the page is right. A conformance check records each requirement as met, partly met, not met or not applicable, and not applicable is not open to a flow that is performed without its message. The asset identification profile stays where it is and is listed beside it.
64. **Payment messages do not apply where an ERP pays.** [Payment Authorized](../03%20-%20Messages/Payments/Payment%20Authorized.md) and [Payment Executed](../03%20-%20Messages/Payments/Payment%20Executed.md) carry payments made through the protocol. An orchestrator that pays and collects in an ERP or accounting system outside the exchange writes neither, and the payments module of the orchestrator profile is not applicable to it. Its invoice messages still apply, including [Invoice Disputed](../03%20-%20Messages/Payments/Invoice%20Disputed.md) and [Invoice Cancelled](../03%20-%20Messages/Payments/Invoice%20Cancelled.md). A connected ERP may report a payment with Payment Executed as payment agent. No schema change.
65. **Identifier schemes for VAT and company register numbers.** [Actor Reference](../02%20-%20Foundational%20Structures/Actor%20Reference.md) lists `urn:ipproto:scheme:vat` (the VAT identification number with the issuing authority's country prefix, no spaces) and `urn:ipproto:scheme:companyRegister` (the number as the register prints it). Because one register number recurs across registers, an identifier entry gains the optional field `registrationAuthority`, required with `companyRegister`; its recommended value is the register's code in the GLEIF Registration Authorities List. The schemes are standard values of an open field, so a scheme name of an implementation's own remains possible as a namespaced URN; a scheme in an implementation's own namespace was not chosen for these two, because the need is not one implementation's.
66. **An Actor Reference becomes immutable when it is first published.** The immutability that [Actor Reference](../02%20-%20Foundational%20Structures/Actor%20Reference.md), *Behavior*, has stated since 0.1 runs from the moment another actor can first see the reference: its `actorUri` appears in a message sent to another actor, or the reference is served through record resolution. Before that the actor that keeps it may correct it, for instance a legal name found to be misspelt during verification. Adding an identifier or recording its verification describes the same actor and does not need a new URI.
67. **Every action between two organizations is journaled as a protocol message.** A message is a record, not only a transmission: it exists once produced and recorded, whether or not a transport carried it. An orchestrator records every action between two organizations that it performs or carries, and for which the protocol has a message, as that message, also where all parties work on its own platform. Open services are included: invitations, attestations, bids, withdrawals, awards and declines are [procurement](../03%20-%20Messages/Procurement/Bid%20Invitation.md) messages even when none leaves the platform. The originator is the organization that acted, not the platform, and the parties to a message can obtain it. Written as requirements OR-J1 to OR-J3 of the orchestrator profile in [Conformance](../01%20-%20Front%20Matter/Conformance.md).

## Version 0.6.0 (ratified 2026-11-09)

What a provider instructed directly by its client needs in order to conform: the question whether a firm that does the work, instructed by its client with no orchestrator and no tender, can conform to the standard. Decided by the maintainer on 2026-11-09 as the first of three releases; the litigation module and mandate pricing, and invoicing for firms, follow in later versions. Version 0.6.0 is a minor version under the pre-1.0 rule of [VERSIONING](../../VERSIONING.md) and not purely additive: decisions 73 and 74 relax three rules, and decisions 72 and 79 tighten three. A pre-1.0 MINOR may do so where its scope needs it, each change recorded here, as 0.3 did.

68. **A provider profile.** [Conformance](../01%20-%20Front%20Matter/Conformance.md) carries a second role profile, for the actor in the role `workProvider`, instructed by an orchestrator or directly by its client. Core requirements: every Work Instruction and Mandate Instruction is answered, a refusal with its closed reason category; under a mandate it acts within the mandate's scope; a conflict check it records is recorded with Conflict Check Attested; in a direct engagement it holds the status claim and closes the workstream; it reports the lifecycle of the milestones it performs and sends Milestone Failed only for its own work (decision 62); court-ordered and statutory deadlines are Deadlines, never service levels; deliverables carry Document References; it invoices on the milestones of the workstream it shares with its requester, corrects only by cancellation and reissue and answers an accepted dispute with a cancellation; it journals actions taken outside the protocol as messages, the other party's under `recordedBy`; it follows the addressing rule and never discloses its client through the protocol. Conditional modules: bidder-side procurement; sub-delegation, which applies requirements OR-W1 to OR-W4 and OR-I1 to OR-I5 of the orchestrator profile to the provider in the orchestrator's place; payments; assets. A general requirement G11 states the rules for privileged messages (decisions 76 and 77) for every actor.
69. **A direct engagement needs no orchestrator.** A client and a provider may share one workstream with no orchestrator between them: the client as `workRequester`, `accountableTo` and usually `payor`, the provider as `workProvider` and `primary` actor. Either party may create the workstream: the client with its instruction, or the provider by recording the client's instruction given outside the protocol, the message staying the client's under `recordedBy`. The provider holds the claim over status updates and resulting assets that an orchestrator holds elsewhere; the client holds the corporate claim over goal and chain. The wording that assumed an orchestrator is corrected: who generates a workstream URI and a milestone URI ([Workstream](../02%20-%20Foundational%20Structures/Workstream.md), [Milestone](../02%20-%20Foundational%20Structures/Milestone.md)), the purpose and producer of [Work Instruction](../03%20-%20Messages/Work%20Instruction/Work%20Instruction.md), the recipients of [Work Requested](../03%20-%20Messages/Workstream%20Lifecycle/Work%20Requested.md), and the producers of Request Declined and Workstream Completed. See *Direct engagement* in Workstream.
70. **A mandate covers a workstream.** A new message, [Mandate Instruction](../03%20-%20Messages/Work%20Instruction/Mandate%20Instruction.md), in the Work Instruction category: the work requester instructs a provider with a whole matter, within a `mandateScope` (the matter in words, and optionally the milestone categories, jurisdictions, assets and rights it covers, what it excludes and a last day for adding work). It may carry `conflictParties`, an `agreedPrice`, service levels, a response deadline, known deadlines, documents and expected deliverables, all optional; only `workstreamReference`, `instruction` and `mandateScope` are required. It is answered with Instruction Accepted or Instruction Declined, whose `instructionReference` names it; an accepted mandate commits the workstream. Decision 60 is not touched: Work Instruction keeps its required service levels, response deadline and deliverables, and a mandate states only clocks that were agreed. Pricing models specific to mandates are left to a later version.
71. **A provider may add milestones, but only under a mandate and within its scope.** This amends the claims model of decision 48, under which only the corporate claim changed the goal or the chain. Under an accepted Mandate Instruction the provider holds a mandate claim over adding milestones to `milestoneChain` that lie inside `mandateScope`: in a listed category and jurisdiction, on a listed asset or right, and not after `validUntil`, where these are given. Such a milestone is `committed` when added, without Goal Decomposition or Orchestration Committed, with the provider as `primary` and the client as `accountableTo`. The corporate claim keeps the goal: changing `goalStatement`, adding or removing assets or rights still to be created, and removing or altering milestones the client set stay with the client. A milestone outside the scope is not covered, whatever is asserted; the client widens the mandate with a new Mandate Instruction for the same workstream. As in decision 48, an Authority Claim names a section and not an operation, so the line is a rule of the page that both claimants and receivers observe. A provider under a Work Instruction gains nothing by this decision.
72. **A Deadline structure.** [Deadline](../02%20-%20Foundational%20Structures/Deadline.md) carries a time limit the parties did not set for each other: `deadlineKind` `courtOrdered`, `statutory`, `agreed` or `hearing`, or a namespaced URN; an optional `basis` (text, provision, document), an optional `trigger` (event type from an open vocabulary, date, document); `dueDate`, optional `dueAt` and `jurisdictionCode`; the holder's own `reminderDates`; an extension as a `supersedes` link to the deadline replaced, with the granting document; a closed `status` (`open`, `met`, `missed`, `superseded`, `withdrawn`), and `metBy`, required when met. A hearing is an appointment: `deadlineKind` `hearing` requires `appointment` with its start, and no other kind carries one. It is used to type `failureImpact.affectedDeadlines` of Milestone Failed (each entry a Deadline or a `deadlineUri`) and `goalConstraints.deadlineConstraints` of Workstream and Work Requested, both of which existed in prose without a shape; typing them is a tightening, which no published example is affected by. Milestone and Mandate Instruction gain optional `deadlines`. A deadline is not a service level, and neither is derived from the other: decision 60 stands. Values specific to one kind of proceeding go into vocabularies, not into this structure.
73. **The conflict check serves instructions and requests as well as invitations.** [Conflict Check Attested](../03%20-%20Messages/Procurement/Conflict%20Check%20Attested.md) gains `subjectReference`, whose `subjectType` is `bidInvitation`, `workInstruction`, `mandateInstruction` or `request`. `invitationReference`, required until 0.6, is required only where `subjectReference` is absent: a relaxation of a required field in a MINOR. The producer may be a `workProvider` as well as a `bidder`. A checked party may be given with its role, as a `conflictParties` entry, as well as a bare Entity Reference (a second relaxation). `checkedAt` is added. The closed outcome gains `clearedAfterReview`: a possible conflict reviewed and released by a responsible person, with the effect of `clear` and, like `conflict`, no detail. An attestation may be kept as an internal record with an empty `addressedTo`. The message stays in the Procurement category.
74. **Conflict parties are shared, and an Entity Reference can carry identifiers.** The `conflictParties` entry of Bid Invitation (`partyRole`, `party`) is the shared shape for Work Instruction, which gains optional `conflictParties`, for Mandate Instruction and for the checked parties of Conflict Check Attested. `partyRole` gains `applicant` and accepts namespaced URNs, so that a vocabulary of a proceeding can name further roles (a third relaxation: the list was closed). Where work is passed on, the requester carries the parties down, re-stated under its own name where the source would reveal the customer. [Entity Reference](../02%20-%20Foundational%20Structures/Entity%20Reference.md) gains optional `identifiers`, with the shape of an Actor Reference identifier, and `aliases`.
75. **The addressee may record the other party's message.** [Common Envelope](../02%20-%20Foundational%20Structures/Common%20Envelope.md) says explicitly that the actor a message is addressed to may record it on the originator's behalf, as a provider records its client's instruction received by letter or e-mail; decision 56 already allowed it, and every example showed the other direction. The envelope gains optional `recordedFrom` (`channel` from an open list, `sourceDocument`, `receivedAt`), used only together with `recordedBy`. An originator-confirmation status was not added.
76. **A confidentiality marking.** The envelope gains optional `confidentiality` with `level` `privileged`, `confidential` or `normal`, and an optional `basis` URN. Under `privileged`: no broadcast, no `subscriptionInvitations` on an Asset Bootstrap, records named in the message resolved only for its originator and addressees, no forwarding, and no lookup of the workstream's assets against third-party services. A workstream is privileged once one of its messages is. The protocol does not decide whether content is in fact privileged.
77. **A lookup discloses interest.** [Asset Identification and Resolution](../02%20-%20Foundational%20Structures/Asset%20Identification%20and%20Resolution.md), §4, states that a representational actor is never required to resolve assets, and that assets of a privileged workstream are not resolved against third-party lookup services, because the query itself reveals interest in the asset.
78. **One spelling and one copy of the asset identification profile.** The scheme is `urn:ipproto:scheme:internalReference`, as on every other page and in the examples; the profile's one occurrence of `internal-reference` is corrected. The root-level `Asset-Identification-and-Resolution.md`, a copy that had stayed at the state of v0.1, is replaced by a pointer to the profile under `spec/`, which is the only copy from now on.
79. **`protocolVersion` has a pattern.** The envelope schema requires `^\d+\.\d+$`: MAJOR and MINOR, no patch number. A tightening, made now rather than at 1.0 because every published message already follows it.
80. **No normative change in a patch.** Version 0.4.1 released three sender rules as a patch (decisions 53 to 55). VERSIONING.md now says that a rule changing what a sender or a receiver does is a MINOR even when no schema changes, and records 0.4.1 as the exception that will not be repeated.
81. **Every release publishes a checksum.** `scripts/release-checksums.sh` prints a SHA-256 manifest of every file of a tagged tree and the manifest's own digest. The manifest is attached to the GitHub Release, and the digest is recorded in `RELEASES.sha256`, which carries it for every release from v0.1.0 on. The tags were re-created once, on 2026-10-30; a pinning implementer can now verify a release by its contents.

## Version 0.7.0 (ratified 2026-11-09)

The litigation module and mandate pricing, the second of the three releases decided by the maintainer on 2026-11-09. A provider instructed with a whole matter could not state the price such a matter usually has, and a provider conducting a case before a court could not describe the case, its parties, the role of each patent or the documents of the court. Version 0.7.0 is a minor version under the pre-1.0 rule of [VERSIONING](../../VERSIONING.md) and not purely additive: decisions 86 and 90 relax two rules and decision 92 adds one sender rule for every actor, each recorded here. Litigation specifics are a conditional module of the provider profile and vocabulary values; none is a requirement for every actor.

82. **A flat fee per period.** `priceBasis` of [Agreed Price](../02%20-%20Foundational%20Structures/Agreed%20Price.md) gains `periodicFlat`: `amount` is the fee for each period, and `periodicity` (`monthly`, `quarterly`, `semiAnnual`, `annual`, closed) is required with it and not used otherwise. Line items of such a price break down the fee of one period. A new value of a closed enumeration: a 0.6 receiver that validates strictly rejects it, as VERSIONING.md, rule 2, foresees. A cap needed nothing new: `capped` has existed since 0.2, as has the optional `quantity` of a line item, and neither is duplicated.
83. **Rates per role or per timekeeper.** An Agreed Price may carry a `rateTable` for `hourly` and `capped` prices. Each entry has a `rateRole` (from `urn:ipproto:rateRole:`: `partner`, `counsel`, `seniorAssociate`, `associate`, `patentAttorney`, `trainee`, `paralegal`, `technicalExpert`, or a namespaced URN), a `timekeeper` (the provider's own identifier for one person) or both, a `rate` and an optional `rateUnit` (`hour`, `day`). `amount` stays required: under `hourly` it is the rate for time the table does not cover, and repeats the table's highest rate where the table is complete; under `capped` it stays the ceiling. A timekeeper entry takes precedence over a role entry for the same person.
84. **A budget is not a cap.** The difference holds, so a `budget` is added beside the cap rather than merged into it. Under `capped` nothing above `amount` may be invoiced, whatever is agreed later. A `budget` (`amount`, `onExceeding` `notify` or `approvalRequired`) limits nothing that is invoiced: it states what the parties expect and what the provider does before exceeding it, carry on after telling the requester or stop until a new budget is agreed. It differs from a milestone's `estimates`, which are one side's view and bind nobody. It is carried beside an `hourly`, `capped` or `periodicFlat` price, and below the cap under `capped`. How the provider gives notice stays outside the protocol (decision 42); a new budget is a change to the price.
85. **A statutory fee schedule as a floor, and the price of a mandate.** An Agreed Price may name a `statutoryFeeFloor`: a `feeSchedule` as a namespaced URN of the authority that defines it, an optional `valueOfMatter` and a note. The fee charged is not below what the schedule yields for the work done; the protocol computes and checks nothing, and defines no standard schedule. [Mandate Instruction](../03%20-%20Messages/Work%20Instruction/Mandate%20Instruction.md) carries the same Agreed Price, so all of decisions 82 to 85 apply to a mandate; decision 70 had left mandate pricing to a later version. A milestone the provider adds under a mandate whose price is `hourly`, `capped` or `periodicFlat` is charged under that price and needs no `agreedPrice` of its own. `officialFee` is stated to include court fees; no line item type is added.
86. **A Work Instruction recorded by its provider needs no invented clocks.** Since the Mandate Instruction exists (decision 70), the three required fields of [Work Instruction](../03%20-%20Messages/Work%20Instruction/Work%20Instruction.md) were checked against the cases that remain. One remains: a client instructs its counsel with one piece of work by letter or e-mail, without agreed clocks, and counsel records the instruction (decision 75) and answers it. Decision 60 forbids inventing a service level, and a response deadline for an instruction already answered describes nothing. Where the envelope carries `recordedBy`, naming the addressee, `serviceLevels` and `responseDeadline` are therefore present only where they were agreed or set: a relaxation of two required fields in a MINOR. The schema checks the presence of `recordedBy`; that it names the addressee is a rule of the page. Everything else stays: an instruction its requester sends itself, and every instruction passing work on (OR-I2), keeps the required clocks. `expectedDeliverables` stays required, because a single piece of work always has an output the provider can name and decision 60 forbids only placeholders; a matter whose outputs cannot be named on the first day is a mandate. `agreedPrice` stays required. Decision 60 is confirmed for every instruction that is sent rather than recorded.
87. **Proceedings and their parties.** [Workstream](../02%20-%20Foundational%20Structures/Workstream.md) gains optional `proceedings`. Each entry has a `proceedingUri` (`urn:ipproto:proceeding:{uuid}`), a `proceedingType` (from `urn:ipproto:proceedingType:`: `infringement`, `revocation`, `counterclaimForRevocation`, `declarationOfNonInfringement`, `provisionalMeasures`, `opposition`, `appeal`, `other`), a `forum` as an Entity Reference, so that a court need not be an actor, an optional `forumDocketNumber` and `instance` (`firstInstance`, `appeal`, `furtherAppeal` or a URN), at least one party, and optional `relatedProceedings` (`appealFrom`, `counterclaimIn`, `consolidatedWith`, `stayedPending` or a URN). A party has a `partyRole` towards the client (`client`, `adverseParty`, `intervener`, `other` or a URN), the party as an Entity Reference, and an optional `proceduralPosition` in the proceeding (from `urn:ipproto:proceduralPosition:`). The proceedings are carried only to the workstream's own actors, in messages marked at least `confidential` (decision 76); work passed on carries only what the provider further down needs, re-stated under the requester's own name, and a Bid Invitation with a withheld requester carries no docket number. The parties of a proceeding are conflict parties too; `conflictParties` on Work Instruction and Mandate Instruction (decision 74) is unchanged.
88. **Two workstream types; the forum is not a type.** The workstream types gain `infringementAction`, with any counterclaim raised in it, and `nullityAction`, an action before a court to revoke a right brought on its own; an opposition before an office stays `opposition`. A type for actions before one particular court was considered and not added. A workstream type names the kind of work, not where it is done: `opposition`, `appeal` and `recordal` do not say which office hears them, and decision 72 put values specific to one kind of proceeding into vocabularies. The court is the `forum` of the proceeding. A further instance is `appeal`, with the instance in `proceedings`.
89. **The role of an asset in a dispute.** Workstream gains optional `assetRoles`, beside `assetReferences` and replacing nothing: `assetUri` (an entry of `assetReferences`), `role` (`patentInSuit`, `challengedPatent`, `counterAsserted`, `other` or a URN) and an optional `proceedingReference`. One asset may have one role per proceeding. Prior art is not an asset of the workstream; it is a Document Reference, typically an `exhibit`.
90. **A document's originator may be an Entity Reference.** `originator` of [Document Reference](../02%20-%20Foundational%20Structures/Document%20Reference.md), an Actor Reference URI since 0.1, may now also be an Entity Reference, for an originator that takes no part in the exchange: a court, the opposing party. A relaxation of the type of a required field in a MINOR. An originator that is an actor is still named by its URI. A receiver that read `originator` as a URI in every case must expect an object.
91. **Court documents and when they were served.** The document types gain `pleading`, `exhibit`, `courtOrder`, `courtDecision` and `proofOfService`, and `filingReceipt` covers a filing received by a court. A Document Reference gains optional `servedAt` and `receivedAt` (date-time or date): facts about the copy of the party for which the issuer of the reference acts, so that each party states its own. A Document Reference gains optional `courtDesignation` (`designation`, required, as the forum writes it, and optional `proceedingReference`, `side` and `sequenceNumber`) for exhibits. A [Deadline](../02%20-%20Foundational%20Structures/Deadline.md) whose trigger is `service` or `notification` and names a `triggerDocument` takes its `triggerDate` from that document's `servedAt` or `receivedAt`, unless the law deems the event to have happened on another day; the deadline's `triggerDate` then governs the counting, and the document keeps the record of what happened.
92. **Natural persons get data minimisation.** [Entity Reference](../02%20-%20Foundational%20Structures/Entity%20Reference.md) gains optional `entityKind` (`legalPerson`, `naturalPerson`, closed). An Entity Reference that names a natural person carries no more personal data than the work needs: no national identity number, tax number or date of birth for matching, no identifier that an office, court or register does not need for the work, no aliases beyond names the person is known under for the work. A timekeeper in a rate table is named by the provider's own identifier. Written as general requirement G12 of [Conformance](../01%20-%20Front%20Matter/Conformance.md). A new sender rule for every actor, and so a tightening: no schema checks it, and no published example is affected.
93. **No originator-confirmation status.** Decision 75 left it open; it is not added. A message does not change once produced, and a confirmation comes after the recording, so a status fixed at recording would say nothing a receiver can rely on, and a status that changes would need a message the protocol does not have. The originator confirms by acting on the recorded message or by producing the message itself; a written confirmation is kept as the `sourceDocument` of `recordedFrom` or as a further document. [Common Envelope](../02%20-%20Foundational%20Structures/Common%20Envelope.md) says so.
94. **A litigation module of the provider profile.** [Conformance](../01%20-%20Front%20Matter/Conformance.md) adds a conditional module for a provider that conducts proceedings before a court or a tribunal, PR-LT1 to PR-LT5: proceedings and parties in `proceedings`, asset roles in `assetRoles`, court documents with their types, an Entity Reference originator where the court is not an actor and `servedAt` where a period runs from service, court time limits and hearings as Deadlines whose trigger names the served document, and the confidentiality of proceedings. The milestone categories gain `pleadingDrafting`, `courtFiling`, `hearingAttendance` and `appealFiling`, and the deliverable types `briefDraft` and `hearingReport`. A provider that never goes to court claims the profile without the module; nothing in it binds any other actor.

## Version 0.8.0 (ratified 2026-11-09)

Invoicing for firms, the last of the three releases decided by the maintainer on 2026-11-09. A provider instructed directly could conform since 0.6 and price a matter since 0.7, but its invoice could not show what a firm's invoice holds: the time entries, the VAT category of each line, a court fee passed on at cost, the payor's VAT number, or that a charge is shared between two clients. Version 0.8.0 is a minor version under the pre-1.0 rule of [VERSIONING](../../VERSIONING.md). It relaxes one rule (decision 96) and tightens none: every sender rule it adds applies only to a field added in 0.8, so no message valid under 0.7 becomes invalid and no 0.7 sender has to change. Line detail is optional for every actor. Open Question 7 is ratified (decision 102).

95. **Line detail for time entries and expenses.** An invoice line of [Invoice Issued](../03%20-%20Messages/Payments/Invoice%20Issued.md) gains optional `lineId` (the payee's identifier, unique within the invoice), `quantity`, `unit` (`hour`, `day`, `item`, `page`, `word` or a namespaced URN; required with `quantity`), `unitPrice`, `serviceDate`, `timekeeper`, `rateRole` and `billingCodes` (`codeSet` as a namespaced URN, `codeType` `task`, `activity`, `expense` or `other`, closed, and `code`). A time entry is one line; hours are stated to one decimal; `amount` is `quantity` times `unitPrice` rounded to the minor unit, and stays required and authoritative where the payee charges less. `timekeeper` and `rateRole` are those of the `rateTable` of decision 83, so that each rate can be checked; G12 applies to the timekeeper. The protocol defines no code set: the UTBMS code sets are named only as an example. An electronic billing file such as a LEDES 1998B file is a Document Reference of the new type `billingDetail`, named in the new optional `supportingDocuments` of the invoice; both a file and line detail may be given, and then agree. All of it is optional for every actor and every profile.
96. **A disputed line may be named by its `lineId`.** An entry of `disputedLines` in [Invoice Disputed](../03%20-%20Messages/Payments/Invoice%20Disputed.md) names its line by `lineIndex`, by the new `lineId` or by both; `lineIndex` was required and is now one of two. A relaxation of a required field in a MINOR, as decisions 73 and 86 were. `lineIndex` keeps working for every invoice. With both, they name the same line, and a payee that finds they do not follows `lineId`. A receiver that relied on `lineIndex` being present must expect an entry with `lineId` only.
97. **`issueDate` is conditional, and a milestone line may state its period.** Invoice Issued gains `issueDate`, the date of issue printed on the document. It is required when the invoice carries a `taxBreakdown` and optional otherwise. Making it required for every invoice was considered and rejected: every invoice valid since 0.2, every published example among them, would become invalid, and a minor version does not do that without a reason that outweighs it; the invoice document always carried the date, and an invoice that does not state its tax in detail loses nothing without it. The schema enforces the condition. A milestone line gains optional `servicePeriod` (`from`, `to`, inclusive), the counterpart of the `billingPeriod` of a subscription line (decision 50), and is rejected on a subscription line. A line carries at most one of `servicePeriod` and `serviceDate`.
98. **VAT categories per line and a breakdown, in the terms of EN 16931.** A line may carry `taxCategory`: `categoryCode`, one of the EN 16931 VAT category codes (`S`, `Z`, `E`, `AE`, `K`, `G`, `O`, `L`, `M`) as a closed enumeration the protocol does not extend, `ratePercent` (required except for `O`) and an optional exemption reason and reason code. Invoice Issued gains `taxBreakdown`, one entry per category and rate with `taxableAmount` and `taxAmount`, required where any line carries a category and with the new treatment `perLine`, which states that the lines are treated differently. Where one line carries a category, every line that is not a pass-through line does; the breakdown adds up to the lines, `taxAmount` to the breakdown, and the total to the lines plus tax. The invoice-level `taxTreatment` stays required and valid as before; where categories are given, a treatment other than `perLine` agrees with them as the table on the page shows, and a receiver that finds them inconsistent follows the categories. The schema checks presence and codes; the sums are sender rules.
99. **Pass-through lines.** A line may carry `passThrough: true`: it passes on, at cost, an amount the payee paid in the payor's name and on its account, outside its own VAT base, such as a court fee advanced on filing. Such a line carries no `taxCategory`, which the schema enforces, appears in no breakdown entry, and is part of `totalAmount`. It does not make an invoice `perLine`. Whether an amount may be passed on outside the VAT base is a question of the law that applies to the payee; the flag records the payee's position. An expense bought in the payee's own name is a `disbursement` line with a category, not a pass-through line.
100. **Tax identifiers and the buyer reference.** `payee` and `payor` of Invoice Issued gain an optional `taxIdentifier` of the identifier shape of [Actor Reference](../02%20-%20Foundational%20Structures/Actor%20Reference.md), with the scheme `urn:ipproto:scheme:vat` of decision 65 for a VAT number. Decision 65 already allowed a VAT number on the Actor Reference; the invoice now says under which of an actor's numbers it is invoiced, and the number is one of those the Actor Reference lists where it lists any. The invoice gains an optional `buyerReference`, the reference the payor asked to be quoted. Both parties have a `taxIdentifier`, not only the payor, because the payee's number belongs on the invoice as much as the payor's.
101. **A structured invoice document wins.** Invoice Issued gains optional `invoiceDocumentSyntax`: `en16931Cii`, `en16931Ubl` or a namespaced URN. Where it names an EN 16931 syntax, every value the message shares with the document is the document's value and the message does not contradict it; the message may carry less, and may carry what the document has no place for, such as milestone references. A receiver that finds a contradiction follows the document and may dispute with `formalDefect`. Where the document is not structured, the rule of 0.2 stands: the document is the invoice in the legal sense. National e-invoicing rules are not named as requirements: whether an invoice must be electronic is the law of the payee, outside the protocol ([Non-Scope](../01%20-%20Front%20Matter/Non-Scope.md)).
102. **Open Question 7 is ratified.** The tax treatment vocabulary of 0.2, extended in 0.5, is ratified with its five values unchanged and `perLine` added, open to custom values; the provisional marking is removed. The question's points are answered by decisions 98, 99 and 101: per-line categories and a breakdown, pass-through lines, several rates as several breakdown entries, alignment with the VAT category codes of EN 16931. Withholding tax stays outside the breakdown and is stated with a custom treatment or in the document. The question is kept in [Open Questions for Consortium](Open%20Questions%20for%20Consortium.md) with its answer, as questions 1 to 6 were in 0.1, and is reopenable when a consortium forms. No question is open.
103. **Split payers.** A `payor` entry of the `actorAssignments` of a [Milestone](../02%20-%20Foundational%20Structures/Milestone.md), and of [Service Subscription Started](../03%20-%20Messages/Subscriptions/Service%20Subscription%20Started.md), gains optional `payorShare`, a percentage above 0 and not above 100, rejected by the schema on an entry of another type. Where one payor entry carries a share, every one does, and they add up to 100. An invoice still has one payor: each payor receives its own invoice for its share, and Invoice Issued gains optional `allocation` with `sharePercent` (required), `siblingInvoiceReferences` and a note. The lines and total are the payor's share; rounding differences go to the largest share, or to the first sibling issued where shares are equal. Each sibling is a full invoice with its own tax, so one payor may be taxed and another reverse-charged. Cancelling one sibling does not cancel the others; a change of shares cancels and reissues them all. A milestone with several payors and no shares, valid before, stays valid.
104. **A payment names the invoices it settles; payment status stays out of scope.** [Payment Authorized](../03%20-%20Messages/Payments/Payment%20Authorized.md) and [Payment Executed](../03%20-%20Messages/Payments/Payment%20Executed.md) gain optional `invoiceReferences`, each entry an `invoiceReference` with an optional `appliedAmount`, and Payment Executed may be addressed to the payee where it is an actor. A payee-side Payment Received was considered and not added: most payors pay outside the protocol (decision 64), where no message would be sent either way, and the payee learns of a payment from its bank; a receipt message would carry the payee's reading of its own bank statement back to the payor, who knows it already. Whether an invoice is paid, part paid or overdue is not tracked, and [Non-Scope](../01%20-%20Front%20Matter/Non-Scope.md) says so.
105. **Invoicing requirements in both role profiles.** [Conformance](../01%20-%20Front%20Matter/Conformance.md) adds to the invoice requirements of the provider profile PR-V3 to PR-V6, and of the orchestrator profile OR-V4 to OR-V7, in the core and not in a module, because every provider and orchestrator invoices: tax stated beyond the treatment is stated consistently, with an issue date; an EN 16931 document is not contradicted; a shared charge is invoiced per payor with its allocation; and line detail, where given, follows the rate table and G12. Each applies only where the invoice uses the feature, so the line detail and the tax detail stay optional for every actor. OR-V2 names a disputed line by `lineIndex` or `lineId`. The payments modules gain OR-PA2 (invoice references, Payment Executed to the payee), which a provider claims through PR-PA1.

## Version 0.9.0 (ratified 2026-11-09)

Fixes found in a provider-side implementation of 0.8, decided by the maintainer on 2026-11-09. A provider-side implementation, built against v0.8.0 and validating with a second validator, could not record advisory work that concerns no right, rejected a published example, and had to guess under whose claim the facts of a dispute are recorded and against what a patch path is read. Version 0.9.0 is a minor version under the pre-1.0 rule of [VERSIONING](../../VERSIONING.md): two of its points change what validates, and three state rules, which decision 80 keeps out of a PATCH. It relaxes three rules (decisions 106, 107 and 109) and tightens two (decisions 108 and 110), neither in a schema. Every published example of 0.8 is valid under 0.9, under ajv with formats asserted and under Python `jsonschema` without.

106. **A workstream may have no asset.** [Workstream](../02%20-%20Foundational%20Structures/Workstream.md) required `assetReferences` or `prospectiveRights` since 0.3 (decision 37). Advisory work has neither: a freedom-to-operate opinion on a product, the review of a licence agreement, a question of licensing. The schema's requirement is removed, and a workstream may carry neither. Making the rule depend on `workstreamType` was considered and rejected: custom types cannot be checked against it. The rule is one of practice instead: a workstream about a specific right lists it in `assetReferences` as soon as it is known, at creation where it is known then, and otherwise added later by the holder of the status claim as a fact. Adding a right the work was not about widens the goal and stays under the corporate claim. A relaxation in a MINOR: a receiver that relied on every workstream naming an asset or a prospective right must expect one that names neither. `assetRoles` still names only entries of `assetReferences`, so a workstream with asset roles keeps its assets.
107. **A request for advisory work may have no asset either.** [Work Requested](../03%20-%20Messages/Workstream%20Lifecycle/Work%20Requested.md) carried the same requirement as the workstream. Left in place, advisory work could be done in a direct engagement but not requested through an orchestrator. It is removed as well. A relaxation in a MINOR, for the same reason as decision 106. [Bid Invitation](../03%20-%20Messages/Procurement/Bid%20Invitation.md), [Document Reference](../02%20-%20Foundational%20Structures/Document%20Reference.md) and the provider profile were checked and require no asset.
108. **`proceedings` and `assetRoles` are recorded under the status claim.** Decisions 87 and 89 added the two sections without saying under whose claim they change. They record facts of the dispute, as resulting assets do (decision 48): a proceeding begins, a docket number is assigned, a party joins, a counterclaim makes the patent in suit a challenged patent. Adding and updating them falls under the status claim, held by the orchestrator, or by the provider in a direct engagement. Removing an asset role that changes what the client asked for, such as dropping a patent from the patents in suit, stays under the corporate claim. The litigation module of the provider profile states it in PR-LT2. A rule stated where none was: a receiver that accepted such an assertion under another claim now treats it as not covered, recorded as a tightening, though no schema changes.
109. **No alternative is decided by `format` alone.** Four places offered a date or a date-time as `oneOf` two strings that differ only in `format`: `originationDate`, `servedAt` and `receivedAt` of [Document Reference](../02%20-%20Foundational%20Structures/Document%20Reference.md), and `auditCompletionDate` of [Workstream Completed](../03%20-%20Messages/Workstream%20Lifecycle/Workstream%20Completed.md). JSON Schema 2020-12 treats `format` as an annotation unless a validator opts in, and a validator that does not assert it finds such a string valid under both branches, so `oneOf` fails. The published court-order example failed this way. Each becomes `anyOf`. A relaxation in a MINOR: a validator that asserts formats accepts exactly what it accepted before, since no string is both a date and a date-time, and one that does not now accepts what it rejected. The two other `oneOf`s were checked and kept: the line reference of [Invoice Issued](../03%20-%20Messages/Payments/Invoice%20Issued.md) chooses between `required` sets, and the content of [Data Assertion](../02%20-%20Foundational%20Structures/Data%20Assertion.md) between two `const` values of `contentType`; neither depends on `format`. Every example is now validated in CI by Python `jsonschema` without format checking as well as by `validate.mjs`.
110. **Patch paths are relative to `sectionPath`.** [Data Assertion](../02%20-%20Foundational%20Structures/Data%20Assertion.md) now states that the `path` of every patch operation is a JSON Pointer relative to `sectionPath`, as if the section were the whole document, and `""` names the section itself. Every example already read it so (`/-` under `/legalStatus/events`). A sender that read the paths as absolute to the record diverged from every example; recorded as a tightening.
111. **Example patent numbers are fictional.** The examples used numbers in the format of real publications, low EP numbers among them, which are real. Litigation and opposition examples now use the ST.3 code `XX`, which names no office, in the digit layout of the number it replaces (`XX 0 000 001 B1`). The running example of the EP post-grant flow keeps EP, because it shows the EPO's procedure and the check digit of an EP application number, and uses numbers that cannot exist: application `21000000.0`, publication `EP 0 000 000`. [Conventions](../01%20-%20Front%20Matter/Conventions.md) states the rule for future examples. No message or schema changes.
